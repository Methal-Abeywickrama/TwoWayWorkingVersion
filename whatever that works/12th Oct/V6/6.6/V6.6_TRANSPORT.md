# v6.6: ARQ (TCP-like) and UDP transport blocks with sockets for a daemon

v6.6 is v6.5 (src/dest addressing, TX mute, CSMA) plus two blocks. Your daemon talks to them over local sockets:

```
 your daemon ── TCP 127.0.0.1:5100 ──> [ARQ Transport] ──┐
             <─ (reliable messages) ──                   ├─> Packet Framer -> CSMA -> radio
 your daemon ── UDP 127.0.0.1:5200 ──> [UDP Transport] ──┘
             <─ UDP 127.0.0.1:5201 ── (datagrams)        <── Packet Deframer <- radio
```

| | ARQ Transport (`epy_arq`) | UDP Transport (`epy_udp`) |
|---|---|---|
| Use for | files, anything that must arrive | chat lines, beacons, status |
| Unit | a message of any size, up to 4 MB | one datagram = one radio frame, up to 2046 B |
| Delivery | complete, in order, no duplicates, or reported FAIL | once, no guarantee |
| Destination | one node (0 to 254) | one node, or 255 = every node |
| Sender is told | `SENT` (confirmed by the receiver) or `FAIL` (with reason) | nothing |

Typed messages in the TX Message box still work as before, next to both blocks.

## Start a node

**Node A**

```bash
export CDP_MY_ID=2
gnuradio-companion v6.6_csma_transport.grc &
python3 cdp_sock.py arq-listen --out-dir ~/cdp_inbox &      # prints / saves what arrives (or run your daemon)
```

**Node B**

```bash
export CDP_MY_ID=5
gnuradio-companion v6.6_csma_transport.grc &
python3 cdp_sock.py arq-listen --out-dir ~/cdp_inbox &
```

**Try it from node A**

```bash
python3 cdp_sock.py arq-send --dest 5 --text "hello"
python3 cdp_sock.py arq-send --dest 5 --file photo.jpg     # prints SENT + time + kB/s, or FAIL + reason
python3 cdp_sock.py udp-send --dest 255 --text "beacon"
python3 cdp_sock.py udp-listen                              # on the other node
```

At start the console shows:

```
[ARQ] node 2: daemon socket tcp://127.0.0.1:5100, mss 1000 B, window 8, session 3fa1c2d9
[UDP] node 2: daemon sends to udp://127.0.0.1:5200 (dest 1B + payload, max 2046 B), received datagrams go to udp://127.0.0.1:5201 (src 1B + dest 1B + payload)
```

## Settings (environment variables, read when the flowgraph starts)

| Variable | Default | Meaning |
|---|---|---|
| `CDP_MY_ID` | 1 | this node's ID, unique, 0 to 254 |
| `CDP_ARQ_PORT` | 5100 | ARQ daemon socket (TCP) |
| `CDP_UDP_PORT` | 5200 | UDP: the daemon sends here |
| `CDP_UDP_OUT_PORT` | 5201 | UDP: the block delivers received datagrams here |
| `CDP_BIND` | 127.0.0.1 | Address the block sockets listen on. `0.0.0.0` lets other PCs connect, but then anyone on that network can send through your radio. |
| `CDP_UDP_DELIVER` | 127.0.0.1 | where received datagrams are sent |
| `CDP_ARQ_MSS` | 1000 | Data bytes per radio frame. Lower it (e.g. 512) if big frames are often lost on your link. |
| `CDP_ARQ_WINDOW` | 8 | Segments in flight per destination, at most 32. |
| `CDP_ARQ_RETRIES` | 8 | Transmissions per segment before the message is reported FAIL. |
| `CDP_HOST` | 127.0.0.1 | `cdp_sock.py` only: where the blocks are |

`cdp_sock.py` reads the same variables.

## Socket protocol (for writing your own daemon)

**ARQ**

TCP. Every frame, both ways, is a 4-byte big-endian length, then the body.

| Body | Direction | Meaning |
|---|---|---|
| `01` ref(4) dest(1) data… | daemon → block | SEND: queue a message. `ref` is your number for it. |
| `80` node(1) mss(2) window(1) max_msg(4) | block → daemon | HELLO, sent on connect |
| `81` src(1) data… | block → daemon | RECV: a complete message from node `src` |
| `82` ref(4) dest(1) | block → daemon | SENT: every part of the message was acknowledged |
| `83` ref(4) dest(1) reason(1) | block → daemon | FAIL: 1 no ACK after all retries, 2 bad dest, 3 send queue full (8 MB), 4 message over 4 MB, 5 empty |

- **More than one daemon** can connect: RECV goes to all of them, SENT and FAIL only to the one that sent.
- **Messages that arrive while no daemon is connected** are kept (up to 1000) and handed to the next one that connects.
- **FAIL means "not confirmed".** If only the ACKs were lost, the other node may still have the message.

**UDP**

Plain datagrams.

| Direction | Datagram |
|---|---|
| daemon → `CDP_UDP_PORT` | dest(1) + payload |
| `CDP_UDP_OUT_PORT` → daemon | src(1) + dest(1) + payload. dest is 255 if it was a broadcast. |

**Python**

```python
from cdp_sock import ArqClient, UdpClient
a = ArqClient()                       # a.node, a.mss, a.window, a.max_msg from HELLO
ref = a.send(5, open("photo.jpg", "rb").read())
print(a.wait(ref, timeout=300))       # ('sent', ref, 5) or ('fail', ref, 5, reason)
for ev in a.events():                 # ('recv', src, data) / ('sent', ...) / ('fail', ...)
    ...
u = UdpClient(); u.send(255, b"beacon"); print(u.recv(timeout=5))   # (src, dest, data)
```

## How the ARQ works

- **Segments.** A message is cut into segments of up to `mss` bytes. Each segment gets an 11-byte header with:
  - a sequence number;
  - the sender's "base" (lowest segment still in play);
  - first/last flags;
  - an "ACK now" flag.
- **Window.** Up to `window` segments are in flight per destination. A congestion window halves on a timeout and grows by one per ACK. This stops retransmissions from piling onto a busy channel.
- **ACKs are rare, because each one costs a whole frame on air.**
  - The receiver ACKs on the last segment of each burst (the "ACK now" flag), after every 4 segments, or at the latest 0.5 s after a segment.
  - Each ACK carries the next expected segment, plus a 32-bit bitmap of what arrived beyond it.
- **Losses** are resent early when the bitmap shows a hole. Otherwise they are resent on an adaptive timeout: srtt + 4 × rttvar, between 1 and 8 s, doubled on each timeout.
- **Giving up.** After 8 tries the message is reported FAIL, and the receiver is told (through "base") to skip what is missing. A failed message is never delivered half-built, and the next message still gets through.
- **A restarted node** gets a new random session number. The other node notices it, prints `node 2 restarted ... receive state reset`, and carries on.
- **Every 10 s** the console shows per-peer counters: messages sent and failed, segments sent and resent, in flight, cwnd, srtt and RTO.

The framer and deframer no longer print a line for each transport packet. Typed text is still shown as before.

## Tested here (stubbed GNU Radio, real sockets, simulated radio)

The simulated channel carries one frame at a time. Both nodes contend fairly. Each frame takes 40 to 110 ms of channel access plus its real airtime, and each frame is lost independently with the given probability.

30 kB message, node 2 → node 5:

| Loss | mss 1000, window 8 (default) | mss 512, window 8 | mss 1000, window 16 |
|---|---|---|---|
| 0 % | 3.9 s (7.6 kB/s) | 7.2 s | 4.0 s |
| 10 % | 4.0 s | 10.7 s | 4.0 s |
| 20 % | 10.2 s | 9.9 s | 9.3 s |

- Window 16 gains nothing, because the channel is already full.
- A 300 kB message at 10 % loss took 56 s (5.3 kB/s) and arrived intact.

All passed:
- **Both directions at once:** 20 messages each way at 15 % loss, all in order and intact.
- **Node that doesn't exist:** FAIL, reason 1.
- **Bad requests:** sending to its own ID or to 255 gives FAIL reason 2; an empty message gives FAIL reason 5.
- **Link cut:** the first message fails. A message cut halfway is not delivered in pieces. The next message gets through intact.
- **Sender restarted** in the middle of the traffic: messages from before and after the restart arrive.
- **Receiver daemon connects late:** it gets the kept messages.
- **UDP:** unicast, broadcast, oversize and to-self datagrams rejected. ARQ, UDP and typed text share the channel without picking up each other's packets.
- **Command-line tool:** a 40 kB file arrived byte-for-byte, a UDP beacon arrived, and a clear message is printed when the block isn't running.

These are simulated numbers; on your link, loss depends on frame size and distance.

## Limits

- **ARQ is unicast.** For "everyone", use UDP or send one message per node.
- **No encryption or authentication.** Keep `CDP_BIND` at 127.0.0.1 unless the network is trusted.
- **Your existing `folder_sync_daemon.py` and `cdp_chat.py`** still use ZMQ and the old transport state machine. To use v6.6 they need to send through `ArqClient` / `UdpClient` instead.
- **`mac_ctrl` (optional) on the ARQ block** emits `ok` / `fail` for the CSMA `ctrl` input, which grows the backoff on losses. It isn't connected, because with 2 nodes most losses are noise, not collisions.
