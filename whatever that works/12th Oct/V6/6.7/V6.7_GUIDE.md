# CDP link v6.7: app, dashboard and diagnostics

There are two files. Keep them in the same folder on every PC.

| File | What it is |
|---|---|
| `v6.7_cdp_link.grc` | The v6.6 flowgraph plus three additions: a **Telemetry/Watchdog** block, a **TX probe**, and **SET_\*** parameter blocks |
| `cdp_link_app.py` | One app that holds the chat, the dashboard (live monitor and analysis), the settings and the flowgraph launcher |

The app starts the flowgraph itself. It compiles the .grc with `grcc` and runs it with the window hidden, which saves CPU. If the flowgraph stops, the app restarts it.

## 1. One-time setup (Fedora, each PC)

```bash
sudo dnf install python3-qt5 libiio python3-libiio
mkdir -p ~/cdp && cp v6.7_cdp_link.grc cdp_link_app.py ~/cdp/
```

## 2. Start each node

**Node A**

```bash
export CDP_MY_ID=2
cd ~/cdp
python3 cdp_link_app.py --node $CDP_MY_ID --name Methal
```

**Node B**

```bash
export CDP_MY_ID=5
cd ~/cdp
python3 cdp_link_app.py --node $CDP_MY_ID --name Peer
```

`--node` and `--name` are only needed the first time. They are saved in `~/.cdp_link/config.json`, and after that `python3 cdp_link_app.py` is enough. You can also change the node ID later in **Settings → This node's ID**, then click **Save & restart flowgraph**.

The first start takes about 10–20 s because `grcc` compiles the flowgraph into `~/.cdp_link/build/`. It only recompiles when the .grc changes.

**Start automatically at login.** The app then starts, and the flowgraph with it:

```bash
python3 ~/cdp/cdp_link_app.py --install-autostart      # undo: --remove-autostart
```

**Running the flowgraph from GNU Radio Companion instead.** The app notices a flowgraph that is already running and uses it rather than starting a second one:

```bash
export CDP_MY_ID=2
gnuradio-companion ~/cdp/v6.7_cdp_link.grc &
python3 ~/cdp/cdp_link_app.py --node 2 --no-flowgraph
```

## 3. Tabs

**Chat** works the same as `cdp_chat_v66.py`:
- `#everyone` broadcasts;
- `@node` sends a direct message with ✓ confirmation;
- files go in the 📎 button;
- the history from the old app carries over.

**Dashboard → Live monitor** is the mode to use while the normal apps run. It refreshes once a second and shows:

| Section | What it shows |
|---|---|
| Status line | Whether the flowgraph is running, how many times it has restarted, telemetry live or not, chat socket connected or not |
| **Problems now** | Watchdog problems that are active right now (red) |
| **Radio and PC** | % of samples arriving (should be 100), noise floor, channel busy, TX mute state and write time, TX bursts, CPU, busiest threads, longest time Python was blocked |
| **CSMA** | Frames sent, deferrals, drops, queue and its oldest frame, access delay, own echo vs. slot, current state (stuck in "sending" = stall) |
| **Receiver** | Correlator hits and correlation strength; deframer frames, CRC ok/fail, squelch cuts, frames waiting |
| **ARQ** | Per peer: messages sent, failed and open; segments resent; timeouts; cwnd; srtt/rto; how long the oldest open message has waited |
| **Recent watchdog events** | The latest watchdog events |

The Live monitor has three buttons:
- **Report (this node, last 10 min)** turns the last 10 minutes into a report with findings.
- **Dump stacks** writes where every Python thread is right now to `~/.cdp_link/stacks_node<ID>.txt`.
- **Open logs folder** opens `~/.cdp_link`.

**Dashboard → Run analysis** is the active test. Enter the peer's node ID, pick **quick** (about 40 s) or **full** (about 2 min), and click **Run analysis**. The peer only needs the app running; it answers by itself. The test does four things:
1. sends short and long UDP packets and counts what arrives on each side, which gives loss **in each direction** and round-trip time;
2. sends a reliable 20 kB (quick) or 100 kB (full) transfer and measures goodput, resends and timeouts;
3. asks the peer for its own telemetry (noise floor, sample loss, mute, CPU, events);
4. builds a report that compares the two nodes, with a list of **findings → what to do**.

Reports are saved as HTML, Markdown and JSON in `~/.cdp_link/reports/`. **Send me the .md file** when you want help reading one.

**Settings**
- node ID, name and .grc file;
- start the flowgraph with the app; restart it if it stops; show the flowgraph window (off by default, saves CPU);
- every link parameter (table below);
- **Apply now** changes the parameters in the running flowgraph without a restart. Every value is also saved and used at the next start.
- Node ID, ports and file need **Save & restart flowgraph**.

**Log** shows the app's messages and the flowgraph's console. The console is also saved to `~/.cdp_link/flowgraph_node<ID>.log`.

## 4. Parameters

Each parameter can be set in three places, all of which feed the same `SET_*` blocks in the .grc:
- in the app's **Settings** tab;
- with an environment variable (export it before running GRC);
- by editing the `SET_*` variable block in GRC.

| Setting | Variable | Default | Live? | Notes |
|---|---|---|---|---|
| ARQ segment size | `CDP_ARQ_MSS` | 1000 | yes | 512 is better on weak links; 2037 is the maximum |
| ARQ window | `CDP_ARQ_WINDOW` | 8 | yes | |
| ARQ tries per segment | `CDP_ARQ_RETRIES` | 8 | yes | After this many tries the message FAILs |
| ARQ first / min / max timeout | `CDP_ARQ_INIT_RTO` / `_MIN_RTO` / `_MAX_RTO` | 2 / 1 / 8 s | yes | **Lower max (4 s) = faster recovery after a burst of losses** |
| ACK every / ACK delay | `CDP_ARQ_ACK_EVERY` / `CDP_ARQ_ACK_DELAY` | 4 / 0.5 s | yes | |
| CSMA slot / DIFS | `CDP_CSMA_SLOT` / `CDP_CSMA_DIFS` | 0.015 / 0.020 s | yes | The slot must be longer than own echo + mute write |
| CSMA cw min / max | `CDP_CSMA_CWMIN` / `CDP_CSMA_CWMAX` | 8 / 128 | yes | |
| Radio TX+RX delay, receiver-off guard | `CDP_CSMA_TXDELAY` / `CDP_CSMA_GUARD` | 0.012 / 0.005 s | yes | |
| CSMA sense margin | `CDP_CS_MARGIN` | 6 dB | yes | |
| Squelch margin | `CDP_SQ_MARGIN` | 6 dB | yes | |
| TX attenuation while sending | `CDP_TX_ATT` | 20 dB | yes | |
| TX mute when idle | `CDP_TX_MUTE` | 1 | yes | |
| Deframer debug lines | `CDP_DEBUG` | 1 | yes | 0 saves CPU |
| Ports | `CDP_ARQ_PORT`, `CDP_UDP_PORT`, `CDP_UDP_OUT_PORT`, `CDP_TELEM_PORT` | 5100, 5200, 5201, 5300 | restart | |

## 5. Diagnosing "a packet gets stuck and everything stalls"

The Telemetry block reads every block once a second. It works as a watchdog: when it sees one of the stalls below, it raises an event, and the stall types marked 📄 automatically **dump the stack of every Python thread** to `~/.cdp_link/stacks_node<ID>.txt`, so you can see exactly where the code was stuck. Everything is also logged once a second to `~/.cdp_link/telemetry_node<ID>.jsonl`.

| Watchdog event | Means | Usual cause / fix |
|---|---|---|
| `rx_stream_stalled` 📄 | No samples from the radio for more than 3 s | USB/network link to the Pluto lost (power: use a powered hub, short cable, check `dmesg`). The app restarts the flowgraph when it dies. |
| `samples_dropped` | Less than 99 % of samples arrive | The PC is too slow: window hidden, debug 0, other programs closed, `powerprofilesctl set performance`, laptop on the charger |
| `csma_tx_phase_stuck` 📄 | CSMA has been "sending" for more than 1 s | The attenuation write or TX path is blocked; the stacks show where |
| `tx_path_stalled` 📄 | CSMA releases frames but no samples reach the Pluto sink | TX side of the radio stuck |
| `csma_queue_waiting` | A frame has waited in the CSMA queue for more than 5 s | Channel always busy (noise floor jump, interference) or a TX stall |
| `arq_thread_stalled` 📄 | The ARQ worker thread hasn't run for more than 1 s | A Python lock-up; send me the stacks file |
| `arq_stuck_<node>` | A reliable message has been open for more than 30 s | Many losses in a row with backed-off timeouts; lower the max timeout and fix the weak direction |
| `deframer_waiting` | A frame is held for more than 2 s waiting for more bits | The receiver only processes while the squelch is open, so the end of a frame waits for the next signal. The ARQ resends cover it, but messages arrive late. |
| `python_stall` / `hot_thread` | Python blocked for more than 250 ms / one thread above 90 % of a core | CPU contention; see the busiest threads |
| `no_echo`, `mute_errors`, `mute_off` | Own burst not heard / attenuation writes failing / mute not available | TX not transmitting, radio link, libiio missing |

**When it stalls:**
1. Open **Dashboard → Live monitor** and look at **Problems now**, the CSMA **State** line, and the ARQ "oldest open" column.
2. Click **Dump stacks**. A stalled episode has usually dumped them already.
3. Click **Report (this node, last 10 min)**.
4. Send me three files: the report `.md`, `stacks_node<ID>.txt` and `flowgraph_node<ID>.log`. Do this on both nodes if you can.

## 6. Reading a report for the weak-side problem

- **"this node → peer is the weak direction"** means one direction loses many more packets than the other. Compare the two nodes' noise floor, TX mute and TX attenuation in the **Both nodes** table. Then swap the radios between the PCs: if the weak direction follows the radio, the problem is that radio or its antenna.
- **"the PC loses radio samples"** on one node is the "98 % of samples" warning you saw. It costs that node frames whenever a gap hits a frame. Keep the flowgraph window hidden (the default in the app) and turn deframer debug off.
- **"loss grows with packet size"** means the link is signal-to-noise limited. Use the ARQ segment size the report suggests.

## 7. Notes

- **Test traffic shares the channel** with normal traffic. Run the analysis when the link is otherwise quiet.
- **Hidden flowgraph window.** With the window hidden, the GRC sliders and boxes (TX message, Dest ID) are not visible; use the app's Chat and Settings instead. Tick "Show the flowgraph window" if you want them.
- **Older apps still work.** `cdp_sock.py` and `cdp_chat_v66.py` still work with v6.7, but don't run the old chat app at the same time as this app (both want UDP port 5201).
